## Lo que encontramos al preparar el plan
El roadmap pedía «crear fixtures» para medir. Ya existe casi todo, así que el plan se ajusta para **reutilizar y no duplicar**:

| Ya existe | Dónde | Qué cubre |
|---|---|---|
| Banco de montaje de colecciones | `tests/benchmarks/mounting/collection-mount.bench.ts` | Abre colecciones de 50, 200, 500, 1000 y 3000 peticiones, en `bru` y `yml`, 3 iteraciones cada una |
| Generador de colecciones | `tests/benchmarks/utils/collection-generator.ts` | Crea colecciones reproducibles de N peticiones |
| Banco del runner | `tests/benchmarks/runner/runner-allocation.bench.ts` | Reserva de memoria del runner |
| Valores de referencia por sistema | `tests/benchmarks/mounting/baseline.{ubuntu,macos,windows}.json` | Tiempos esperados (los del proyecto de origen, **no medidos aquí**) |
| Marcas de tiempo en el proceso principal | `bruno-electron/src/utils/benchmark.js` (`checkpoint`) | Activas solo con `BRUNO_BENCHMARK=true` |
| Servidor de pruebas con respuesta grande | `packages/bruno-tests/src/large-payload/index.js` | `GET /large-payload?size=N` (hasta 64 MB), **pero solo devuelve `text/plain`**, no JSON |
| Comando | `npm run test:benchmark` (`playwright.benchmark.config.ts`) | Levanta la interfaz web y el servidor de pruebas y corre `tests/benchmarks/**/*.bench.ts` |

**Pista fuerte, a confirmar midiendo:** en los valores de referencia de Ubuntu, pasar de 1000 a 3000 peticiones (×3) multiplica el tiempo de montaje por **21** en `bru` (8 s → 170 s) y por **7,5** en `yml` (10,7 s → 80 s). De 500 a 1000 (×2) el aumento es de ×2,8 y ×3,1. Hay un punto donde el montaje deja de escalar bien. Es el candidato nº 1 para la corrección de mañana, pero **solo si lo confirmamos en esta máquina**.
